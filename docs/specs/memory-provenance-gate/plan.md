# Memory provenance gate: Brian files, agents propose

Status: PROPOSED (plan revision 8, 2026-09-16, after seven cross-model review rounds and a check against external practice; see `run.md`). Approval state: **not approved**. `/team-build` may not start until Brian approves this exact revision.

Executable acceptance criteria apply (behavior-changing work); the cases in §5 are materialized into the test tree by `/team-build` before any implementation.

## 1. Outcome

**Guarantee.** Durable memory can gain content in exactly two ways: (a) **Brian files it himself** by starting a message with `remember:`; the host writes that whole message, with a provenance line, into one append-only file, and no agent is involved; or (b) **an agent proposes it** and Brian presses Approve on a card that shows the complete proposed text in a canonical visible form. Nothing an agent inferred, summarized, selected, read, fetched, or was told by anyone else lands without that tap. Memory is never rewritten by the host on its own; every landed write is recorded with before/after hashes; a held write lands on approval or is dropped on rejection.

**Why this shape.** Five review rounds tried, in order: proving a session clean (impossible here: shared workspace, tasks, echoes, legacy memory), agent-chosen owner quotes (excerpts change meaning), and agent-chosen whole owner messages (Brian may paste or forward someone else's text). The only automatic path that survived is one where **Brian's own explicit action** is the authorization. That matches what shipped products do (ChatGPT and Claude memory: user-visible, user-controlled entries) and what the research and OWASP ASI06 ask for (provenance on the value, human review of durable writes, an audit trail).

In Brian's terms: **start a message with "remember:" and it's filed on the spot. Anything Atlas or Echo wants to keep in their own words shows up as a card for you.**

## 2. Scope and non-goals

In scope:
- Owner filing: the router turns an owner message beginning `remember:` into a host-authored operation keyed by the message's own id (idempotent), before the message is delivered.
- Memory mounted read-only in the container; a composed-mount check rejecting any writable mount that aliases **any group's** memory tree by source, or the container memory path by destination, with the two required ancestor mounts (`/workspace`, `/workspace/agent`) as the only exceptions; a spawn preflight that refuses a symlinked root or hard-linked files; host-side scaffolding.
- One agent tool, `memory_write`, always held on the owner's card (≤ 2,000 bytes, canonical visible encoding, hold confirmation), with grants bound to the exact request.
- A durable operation ledger: one file per op, hashes committed before mutation, completion by the host sweep, replay commit point = durable insert, a database-level quiesce barrier for maintenance and rollback.
- An advisory `trust` attribute on human messages in the prompt and instruction text.
- Hard cutover, containers first.

Non-goals (settled by review rounds 1–5): any session-cleanliness proof; agent-selected quotes or messages on the automatic path; automatic index maintenance by the host; attesting or cleaning memory written before this feature (12 KB; §7 recommends a one-time read); Codex tool visibility; OKF provenance frontmatter beyond the host-written line; changes to the SessionStart hook; a memory browser CLI.

## 4. Design

### 4.1 Owner filing (`remember:`)

In `src/router.ts` `deliverToAgent`, for each wired agent, when `userId` ∈ `getOwners()`, `content.text` matches `/^\s*remember\s*[:,-]\s*(\S[\s\S]*)$/i`, and the inbound event has a platform message id: before `writeSessionMessage`, insert an op (§4.3) with `request_id = 'owner:' + messageIdForAgent(event.message.id, agent.agent_group_id)`, `kind:'owner'`, `path:'owner-statements.md'`, `mode:'append'`, `content` = the full text, `session_id` = the delivering session, `INSERT OR IGNORE`; an existing row with the same key but different content throws (conflicting reuse); an existing identical row is accepted, so a retry of the same event after a failed mailbox write is idempotent. The insert failing rethrows (message not delivered; router error path logs). Then kick completion (isolated: a completion error is logged, never propagated; the sweep finishes the op). If the platform message id is absent, nothing is filed and a warning names the event (fail closed toward "no automatic write"). Only `content.text` is ever filed; attachments, unfurls and reply context are not. Echo's DM with Brian works the same way.

### 4.2 Read-only memory, mount checks, preflight, scaffold

`buildMounts` adds `groups/<folder>/memory → /workspace/agent/memory` `readonly: true`, `group-state`, after the RW group mount. After the full mount list is composed (allowlisted extras and any provider/gateway contributions), `assertNoWritableMemoryAlias(mounts, protectedRoots)` runs, where `protectedRoots` is the real path of **every** `groups/*/memory` directory on the host (enumerated at spawn), not only this group's. It rejects the spawn if any mount with `readonly: false` has a canonical host source that equals, contains, or is contained by any protected root, **or** a normalized container destination that equals, contains, or is contained by `/workspace/agent/memory` — with exactly two exceptions, the required ancestor mounts `/workspace` (the session directory) and `/workspace/agent` (the group directory), which are shadowed by the read-only overlay. The check also asserts that the overlay is present and ordered after both ancestors. A baseline spawn with the standard mount set therefore passes (M3). Before that, `prepareMemoryRoot(groupDir)` (`src/memory-scaffold.ts`) runs as a preflight that walks the whole tree with `lstat`: a symlink **anywhere** in `memory/` (root, directory, or file), a non-directory at the root or at `memory/system`, a non-regular file at `memory/owner-statements.md`, a real path outside the group's real directory, or any regular file with link count > 1 aborts the spawn with a logged error naming the path and one owner DM notice; nothing is moved. Otherwise it creates `memory/system` and `memory/owner-statements.md` (`---\ntype: owner-statements\n---\n`) when missing and copies the three shipped templates when missing. All host writes into memory (scaffold and op completion) open the target with `O_NOFOLLOW` after re-verifying with `lstat` that every path component below `memory/` is a real directory, so a symlink created between preflight and write cannot redirect them. The container scaffold (`memory/scaffold.ts`, its test, the call in `index.ts:58`) is removed. Reads, `Grep`, and the SessionStart hook are unchanged. The link from each group's `index.md` to `owner-statements.md` is added once at rollout, by hand, with a backup; the host never edits an index.

### 4.3 The door: `memory_write` (held) and the operation ledger

**Tool** (`container/agent-runner/src/mcp-tools/memory.ts`, `memory.instructions.md` ≤ 500 B): `memory_write({ path, mode, content? })`, `mode` ∈ `replace | append | delete`, `content` ≤ 2,000 bytes; always goes to Kobe's card. Emits one `kind:'system'` row `{ action:'memory_write', request_id, path, mode, content }` after local shape validation; returns "requested; Kobe will see a card".

**Host module** `src/modules/memory-gate/` (`index.ts`, `guard.ts`, `request.ts`, `ops.ts`, `sweep.ts`, `migration.ts`, `render.ts`, `quiesce.ts`).

- Registration mirrors self-mod: `registerDeliveryAction('memory_write', enqueueMemoryOp, { guardAction, precheck: validateShape, requestHold: requestMemoryHold, onDeny })`; `registerApprovalHandler('memory_write', retainingReplay)`; a `MODULE-HOOK:memory-gate-ops-sweep` block in `src/host-sweep.ts` calling `completePendingOps()` once per tick.
- **Quiesce (database barrier).** Table `memory_gate_state(id INTEGER PRIMARY KEY CHECK (id = 1), quiesced INTEGER NOT NULL DEFAULT 0, updated_at TEXT)` (same migration). Every op insert is a single statement `INSERT INTO memory_write_ops … SELECT … WHERE NOT EXISTS (SELECT 1 FROM memory_gate_state WHERE quiesced = 1)`, so once the flag is set no insert can succeed regardless of how far an in-flight handler already got; the flag is set and cleared with `ncl memory-gate quiesce on|off` (host-only command, `access: 'hidden'` for agents). Behavior while quiesced: `memory_write` precheck refuses with `notifyAgent('memory writes are paused for maintenance; try later')`; an approved replay whose insert is blocked by the barrier **returns the typed outcome `{ outcome: 'retained' }`** — a small, explicit extension of the approvals response handler (`src/modules/approvals/response-handler.ts`, lead-owned in this build): a handler that returns `retained` makes the response handler transition the row `approved → pending`, skip deletion, skip the resolved notification, and leave the card actionable; every existing handler returns `undefined` and keeps today's behavior. The `remember:` filing whose insert is blocked delivers the message normally, skips filing, and notifies the owner once; completion of already-queued ops continues. Rollback drains only after the flag is set, so nothing can be inserted after the drain count is read.
- `validateShape` (precheck; **no filesystem access**; failure → `notifyAgent` with the reason, no hold): `request_id` ≤ 64; `path` relative, normalized, no `..`, no leading `/`, segments `[A-Za-z0-9._-]+`, ends in `.md`, ≤ 200 chars, not `owner-statements.md`; `mode` valid; `content` string ≤ 2,000 bytes in the canonical encoding when required; quiesce not active.
- **Guard** `defineGuardedAction({ action:'memory.write', grantActionName:'memory_write', decide, grantCoversRequest })`: `decide` performs **no lookups**: non-agent actor → `DENY`; otherwise `HOLD('free-form memory write')`. `grantCoversRequest(grant, input)` returns true only when the grant's payload `request_id`, `session_id`, and `sha256(path|mode|content)` equal the input's. So a fresh dispatch always holds; an approved replay is validated by the framework (`grantSatisfies`: live row, matching action, and this binding) and executes exactly once; a stale, deleted, foreign, or re-targeted grant is refused by the framework.
- **Hold** `requestMemoryHold`: adapter null → `notifyAgent('could not be held right now; retry in a minute')`, return. Owner lookup happens here (failure → `notifyAgent('could not be held; retry')`). Then `requestApproval({ session, agentName, action:'memory_write', payload: { request_id, session_id, path, mode, content, sha256 }, approverUserId, title:'<Agent> wants to write memory', question })` where `question` = path, mode, byte count, sha256, and the content in the **canonical visible encoding** (`render.ts`), which is **injective** (decodable back to the exact bytes, so two different payloads can never render the same): inside a fenced code block, every backslash is written `\\`, every backtick and every C0 control except `\n`/`\t`, every zero-width or bidi control (U+200B–U+200F, U+202A–U+202E, U+2060–U+2064, U+2066–U+2069, U+FEFF), and every character outside the printable BMP is written `\u{XXXX}`; nothing else is altered; lines over 200 characters are hard-wrapped with a visible `⏎` continuation marker that is itself escaped if it occurs in the input. `render.ts` exports the decoder, and G9 asserts round-trip equality and the collision pairs. Cap 2,000 bytes on the encoded form; metadata budget ≤ 700; a rendered `question` ≥ 3,000 characters is refused before sending (`notifyAgent('split into smaller writes')`). Confirm via `getPendingApprovalsByAction('memory_write')` (row with `session_id` and `request_id` matching) → `notifyAgent('held for Kobe's approval: <path>')`; otherwise `notifyAgent('could not be held (no approver or no DM); ask Kobe directly')` + `log.error`. Rejection uses the approvals module's existing path.
- **Approved replay** `retainingReplay`: wraps `reenterGuardedDeliveryAction('memory_write')`. The commit point is the durable op insert: `enqueueMemoryOp` inserts the `queued` row (existing `applied`/`queued`/`prepared` with identical payload → treated as committed), then kicks completion **inside isolated error handling** (a completion, DB, or notification error after the insert is logged and left to the sweep). If the insert itself throws, retry 3 times with a short delay; if it still fails **and no op row exists for the key**, notify the agent and the owner that the approved write was lost and must be re-requested. The approvals module deletes the row after the wrapper returns, so a committed insert always precedes deletion.
- **Enqueue and complete.** `memory_write_ops(agent_group_id, request_id, session_id, kind, path, mode, content, content_sha256, before_sha256, after_sha256, status, attempts, created_at, updated_at, applied_at, PRIMARY KEY(agent_group_id, request_id))`, `status` ∈ `queued | prepared | applied | conflict | abandoned`. Each op touches exactly one file. `completePendingOps()` (kick and every sweep tick) processes ops per group in creation order, serialized per group:
  0. run the same preflight as the spawn on the group's memory tree (`prepareMemoryRoot`: lstat walk, no symlink anywhere, real directory beneath the real group dir, no hard links; scaffolds a missing tree). A refusal leaves every op of the group **queued** for the next tick and writes nothing (the spawn preflight is what tells the owner); it is never a conflict. Owner filing can kick completion before the group's first spawn, so this cannot depend on the spawn having run;
  1. resolve and check the target on the live filesystem (every component below `memory/` is a real directory by `lstat`, the target is absent or a regular file, real path under the group's real `memory/`); for a `prepared` op, first compare the current state (file sha256, or the `absent` sentinel when the file does not exist) with `after_sha256` — a match means a previous attempt already mutated (including a completed `delete`) and the op is marked `applied`; only when preparing a **new** `delete` must the target exist; any other failure here is `conflict` (agent notified), never a write;
  2. for `kind:'owner'`, build the block `\n- <YYYY-MM-DD> Kobe wrote (msg <message id>):\n  <text, each line indented two spaces>\n`;
  3. compute `before_sha256` (current file or `absent`) and `after_sha256` (planned result) and **commit them as `prepared` before touching the filesystem**;
  4. if the file already equals `after_sha256` → `applied`; if it no longer equals `before_sha256` → `conflict`, notify, stop;
  5. mutate (`replace`/`append` = temp file + rename; `delete` = unlink);
  6. mark `applied`; `notifyAgent('memory written: <path>')`; log.
  A filesystem error increments `attempts`, logs, leaves the op `prepared`; after 10 attempts → `abandoned`, agent and owner notified.
- `onDeny`: `notifyAgent('memory request denied: <reason>')`.
- **Fresh request during a database outage.** If the quiesce lookup, owner lookup, or approval persistence throws on a fresh `memory_write`, the handler rethrows; the delivery loop retries three times and then marks the outbound row failed with an error log line. The agent is never told `held` in that case. The tool's own reply and `memory.instructions.md` therefore say: nothing is stored or held until you receive a `held` or `written` notice; if neither arrives within five minutes, ask again. This is the accepted residual for a host database outage; no separate durable retry is built for it (G16 proves no false `held`).

Invariants: no container mount can write under `groups/<folder>/memory/`; the only automatic write is a whole owner message explicitly prefixed `remember:`, keyed by its own id, written by the host into one append-only file; every agent write requires a `pending_approvals` grant bound to the exact request whose card showed the complete content in the canonical visible encoding; `decide` never performs a fallible lookup; every op touches one file with hashes committed before mutation and is completed durably by the sweep; the host never edits an index or any file it did not create.

## 5. Acceptance criteria as test cases

Host (vitest; in-memory DB; temp `groups/` root; `requestApproval`, `notifyAgent`, `getDeliveryAdapter` injected as fakes; owner seeded):
- **G1** `an owner message starting with remember: is filed by the host before delivery` — router delivery of "remember: my flight is Friday" (with a platform message id) fanned to two agents → two ops keyed `owner:<per-agent id>`, each completed into that group's `owner-statements.md` with the provenance block; the mailbox row is written after the op insert; the agent receives `written`; a non-prefixed message, a non-owner `remember:` message, and an owner message without a platform id (warning logged) file nothing.
- **G2** `owner filing is idempotent across a failed mailbox write` — op inserted, mailbox write fails, the same event retried → one op, one block; a same-key op with different content throws.
- **G3** `memory_write is always held with the complete content on the card` — `requestApproval` once, `approverUserId` = owner, `question` contains path, mode, sha256, and the encoded content; no file; `held` notice only after the pending row is found.
- **G4** `an approved replay executes exactly once and a mismatched grant is refused` — replay with the pending row: op `applied`, file written once; a second replay of the same grant with the same request does not write again; a replay whose grant payload differs in `request_id`, `session_id`, or content hash is refused by the framework (`DENY` reason contains `mismatched grant`), nothing written.
- **G5** `rejecting drops` — rejection through the approvals module leaves no file and no op row; agent told.
- **G6** `the replay commit point is the durable insert` — with `getOwners` and every lookup faked to throw, replay still enqueues and the sweep applies; insert fails twice then succeeds → one approval consumed, one op; insert fails four times with no op row → agent and owner told `approved write lost`; insert succeeds but the completion kick throws → no "lost" notice, op `queued`, next sweep applies once.
- **G7** `shape validation refuses escapes, non-markdown, oversize content, bad modes, and the owner-statements file, without touching the filesystem` — `../x.md`, `/etc/x.md`, `a/../../x.md`, `notes.txt`, 2,001 encoded bytes, `mode:'exec'`, `owner-statements.md`: refused, no hold, no filesystem call (spied).
- **G8** `filesystem state is resolved at completion as conflict, never as a lost tap` — approve a `delete` whose target vanished: op `conflict`, agent notified, approval consumed exactly once; approve a write whose target became a symlink escaping memory: the group's preflight refuses, the op stays `queued`, nothing is written anywhere, the approval is consumed exactly once (the op completes once the link is removed).
- **G9** `the canonical visible encoding is injective, exposes hostile content, and the rendered card never exceeds 3,000 characters` — closing fence, backslashes, zero-width and bidi characters, a Slack mention, a link, 200+ character lines: visible escapes or wrapped text, no unescaped ```; `decode(encode(x)) === x` for every fixture; the collision pairs (a literal `\u{202E}` string vs. the U+202E character; literal spaced backticks vs. a closing fence; a literal `⏎`) encode differently; maximum-size input renders < 3,000; an input whose encoding would exceed the budget is refused with "split into smaller writes".
- **G10** `ops for one group are serialized and each touches exactly one file` — two concurrent owner ops land in dispatch order; no `*.tmp` remains; no other file's hash changes.
- **G11** `hashes are committed before mutation and recovery is exact` — `prepared` op whose file equals `after_sha256` → `applied` without a second append; equals `before_sha256` → mutated once; neither → `conflict`; a `prepared` `delete` whose `unlink` succeeded but whose status update failed is recognized on the next tick by the `absent` sentinel matching `after_sha256` and marked `applied`, not `conflict`.
- **G12** `a write whose first attempt fails is completed by the sweep` — injected rename failure; next tick writes once; `attempts = 2`; after ten failures → `abandoned`, agent and owner notified.
- **G13** `hold confirmation fails safe` — `requestApproval` fake creating no row → `could not be held`, error logged, no `held`; adapter null → early notice, no call.
- **G14** `quiesce is an atomic barrier` (exercised through the real `handleApprovalsResponse` path) — with the flag set: `memory_write` refused with the maintenance notice; an approval resolution returns `retained`, the row is back to `pending` with its card still actionable, and nothing is enqueued; a `remember:` message is delivered but not filed and the owner is notified once; a previously queued op is still completed by the sweep. ## 7. Rollout, rollback, safety

Rollout (containers first): `pnpm typecheck && pnpm build`; stamp the upgrade marker; **stop every running agent container** and confirm `docker ps` shows none; restart the host (migration applies; `orphan-at-startup` is the backstop); confirm none running; add the one-line link to `owner-statements.md` in each group's `memory/index.md` (backup first); the first new spawn of each agent gets the RO overlay; only then is the gate declared active. No image rebuild. **Recommended:** Brian reads the existing 12 KB of memory once.

Rollback: (1) `ncl memory-gate quiesce on` (the database barrier: no op can be inserted from this point; approvals resolved after it return to `pending`; owner filing is skipped with a notice; completion continues); (2) stop all agent containers; (3) drain: wait until `select count(*) from memory_write_ops where status in ('queued','prepared')` is 0, then inspect every `conflict` and `abandoned` row by hand; (4) `delete from pending_approvals where action='memory_write'`; (5) revert, rebuild, re-stamp, restart; (6) `ncl memory-gate quiesce off` (the command and table survive the revert only if the rolled-back code still has them; otherwise the row is inert). Memory files are never touched by rollout or rollback. Persona backups restore with `cp`.

Safety: no container mount can write memory; the only automatic path is Brian's explicit `remember:` message, keyed by its own id; the guard performs no fallible lookups and grants are bound to the exact request; the card shows the complete content in a canonical visible encoding with its hash; the approver is the owner role; filesystem state is resolved at completion as conflict, never as a lost tap; ops touch one file each with hashes committed before mutation and are completed durably by the sweep; a quiesce switch makes maintenance and rollback race-free.

Observability: one log line per decision, one per applied op; `ncl approvals list` for holds; `memory_write_ops` queryable with sqlite3.
